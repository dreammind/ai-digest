# 013: CLI と処理全体の統合

- 状態: 実装済み
- 関連: SPEC.md §4（全体フロー）、§6（縮退動作）、§7（`runs`・`digests`）、§9（cron、ログ、失敗通知、ロックファイル）、§13（受け入れ基準）、CLAUDE.md（コマンド、`--dry-run`・`--no-llm`）、001〜012

## 目的
`uv run python -m aidigest.cli run` の 1 回の実行で、取得からメール送信までを流す。
失敗しても途中の状態を壊さず、使った LLM の費用の記録は必ず残し、失敗をログとメールで知らせる。

## 範囲
- 含む:
  - コマンドライン（`run`、`--dry-run`、`--no-llm`）
  - ログの設定、ロックファイル
  - 001〜012 の部品をつないだ処理の流れ
  - お知らせの文言、記事 0 件の日、`--dry-run` の範囲、失敗通知メール
  - `runs`・`digests` への記録と、配信した記事の `status = sent`
  - コミットとロールバック（`llm_calls` を必ず残す）
- 含まない:
  - cron の登録と VPS への反映：014
  - 保持期間による削除：Phase 2 以降

## 追加する設定値
| 変数 | 型 | 既定値 | 用途 |
|---|---|---|---|
| `LOG_DIR` | パス | `logs` | ログの出力先 |
| `LOG_BACKUP_DAYS` | 1 以上の整数 | `30` | ログを何日分残すか（日ごとにローテーション） |
| `LOCK_PATH` | パス | `data/aidigest.lock` | 二重実行を防ぐロックファイル |

## 処理の流れ（`run`）
1. ログを設定する（`LOG_DIR/aidigest.log` に日ごとのローテーション、標準エラーにも出す）。
2. ロックを取る（`LOCK_PATH` を排他ロック）。取れなければ、何もせずに終了コード 2 で終わる。
3. 設定（`.env`、`sources.yaml`、`topics.yaml`、`pricing.yaml`）を読み、DB を開く。
4. `runs` に開始を記録し、**すぐにコミットする**（`llm_calls` の外部キーのため、また途中で落ちても実行の記録を残すため）。
5. LLM の準備：`--no-llm` なら使わない。そうでなければ `LlmClient` を作る。API キーが無ければ（`LlmUnavailable`）使わずに続け、ERROR ログを出す。
6. 取得（004）→ `source_health` に記録 → 既読判定（003）→ 事前の絞り込み（005）→ ローカルスコア（006）→ 再ランク（008）→ 枠配分（009）→ 要約（010）。
7. お知らせを決める（下記）。
8. 当日・当月の費用を求め（007）、HTML を生成し（011）、静的 HTML を書き出す。
9. 送信する（012）。ただし `--dry-run` のときと、記事が 0 件のときは送らない。
10. `digests` を記録し、送った記事の `status` を `sent` にし、`runs` を完了にして、コミットする。
11. 終了コード 0 で終わる。

### お知らせ（011 に渡す文）
| 状況 | お知らせ |
|---|---|
| `--no-llm` | LLM を使わずに作成しました（--no-llm）。要約はありません。 |
| API キーが無い（`LlmUnavailable`） | LLM が使えないため、要約なしで作成しました。設定を確認してください。 |
| 実行の後で、当日または当月の費用が上限に達している | LLM の予算の上限（1 日 $X／1 か月 $Y）に達したため、要約していない記事があります。 |
| `--dry-run` | （メールを送らないので、お知らせは付けない） |

### 記録
- `runs`：`started_at`、`finished_at`、`fetched_count`（取得した記事の数）、`selected_count`（選んだ記事の数）、`sent_count`（送った記事の数。送らなければ 0）、`error`（失敗したときの内容）
- `digests`：`run_id`、`created_at`、`status`、`article_count`、`html`、`article_ids`（JSON の配列）
  | 状況 | `status` |
  |---|---|
  | 送信した | `sent` |
  | `--dry-run` | `dry_run` |
  | 記事が 0 件で送らなかった | `empty` |
  | 送信に失敗した | `failed` |

### `--dry-run` の範囲（決定事項 1）
- メールは送らない（失敗通知も送らない）。静的 HTML は書き出す（プレビューに使える）。
- **記事の状態（`articles` の登録・更新）は残さない**。次の通常の実行で、同じ記事をあらためて処理できる。
- **残すもの**：`runs`、`source_health`、`llm_calls`（使ったお金の記録）、`digests`（`status = dry_run`）。
- 実現方法：処理の最後に、残すもの（`source_health`・`llm_calls`）をいったん読み出してからロールバックし、それらを入れ直して、`digests` と `runs` を記録してコミットする。

### 失敗したとき（決定事項 2）
- 処理の途中で想定外の例外が起きたら：
  1. その実行の `llm_calls` と `source_health` を読み出してからロールバックし、入れ直す（使ったお金の記録を消さない）。記事の状態の変更は残さない。
  2. `runs` に `finished_at` と `error`（例外の種類とメッセージ）を記録し、コミットする。
  3. 失敗通知メールを送る（`--dry-run` のときは送らない）。
  4. ERROR ログに出し、終了コード 1 で終わる。
- 設定の読み込みに失敗（`ConfigError`）・DB を開けない（`DbError`）：`runs` は記録できないので、ログと失敗通知メール（送れる設定があれば）だけ行い、終了コード 1。
- ダイジェストの送信に失敗（`MailError`）：`digests` は `failed`、`runs.error` に記録し、記事の状態はコミットする（`sent` にはしない）。失敗通知メールを送ろうとし（同じ理由で送れないことが多いので、送れなければログだけ）、終了コード 1。
- 失敗通知メール：件名 `[AI Digest] 実行に失敗しました YYYY-MM-DD`、本文は失敗した段階、例外の種類とメッセージ、ログのパス。宛先は `MAIL_TO`。秘密情報は含めない。

### 記事が 0 件の日（決定事項 3）
- メールは送らない。`digests` は `empty`、静的 HTML は書き出す。取得に失敗したソースがあってもメールは送らない（ログには残る）。

## コマンドライン
- `python -m aidigest.cli run [--dry-run] [--no-llm]`
- 終了コード：0 成功（記事 0 件を含む）、1 失敗、2 二重実行で中止（不正な引数のときも argparse の慣習で 2）

- **AC-013-1**: Given 設定値を設定していない / When `Settings` を作る / Then `LOG_DIR`・`LOG_BACKUP_DAYS`・`LOCK_PATH` は表の既定値になる。`.env.example` に載っている（AC-001-13 のテストで確認する）
- **AC-013-2**: Given 正常に取得・要約できるソースと LLM / When `run` を実行する / Then メールが 1 通送られ、静的 HTML が書き出され、`runs` は完了（件数つき）、`digests` は `sent`（HTML と記事の id つき）、配信した記事は `status = sent`、`source_health` と `llm_calls` が記録され、すべてコミットされ、終了コードは 0

- **AC-013-5**: Given `--no-llm` / When `run` を実行する / Then LLM は呼ばれず、記事はタイトルと原文リンクだけで、お知らせ「LLM を使わずに作成しました…」付きのメールが送られる
- **AC-013-6**: Given API キーが無い設定 / When `run` を実行する / Then LLM は呼ばれず、お知らせ「LLM が使えないため…」付きのメールが送られ、ERROR ログが出る（SPEC §6 の「LLM 全体が使えない」）
- **AC-013-7**: Given 実行中に予算の上限に達する / When `run` を実行する / Then 送られるメールに予算のお知らせが付く（SPEC §13「予算上限に達すると LLM 呼び出しが止まり、タイトルのみで配信」）
- **AC-013-8**: Given `--dry-run` / When `run` を実行する / Then メールは送られず、静的 HTML は書き出され、`articles` は実行の前と同じで、`runs`・`source_health`・`llm_calls`・`digests`（`dry_run`）は残る。続けて通常の `run` を実行すると、同じ記事が処理されて送られる

- **AC-013-11**: Given `topics.yaml` が不正 / When `run` を実行する / Then 失敗通知メールが送られ、終了コードは 1
- **AC-013-12**: Given ほかの実行がロックを持っている / When `run` を実行する / Then 何もせず（取得もしない）、終了コードは 2
- **AC-013-13**: Given ダイジェストの送信が失敗する / When `run` を実行する / Then `digests` は `failed`、`runs.error` が記録され、記事は `sent` にならず、終了コードは 1

## 実装方針（参考）
- モジュール：`src/aidigest/cli.py`（`main(argv) -> int`、`python -m aidigest.cli` で実行）。処理の流れは、外部とのつながり（HTTP クライアント、LLM、メール送信、時計）を引数で差し替えられる関数にする
- テストは、HTTP を `httpx.MockTransport`、LLM を偽物、メール送信を偽物に差し替えて、処理全体を通す（実際の外部アクセス・送信はしない）
- ロックは `fcntl.flock`（VPS は Ubuntu、開発は macOS で、どちらでも使える）

## 決定事項
1. **`--dry-run` は「メールを送らない・記事の状態を残さない」**：CLAUDE.md の「送信・DB 更新なし」と SPEC §7 の `digests.status = dry_run` の食い違いを、こう解く。記事の状態を残さないので、dry-run で試した記事も翌日の通常の実行で配信される。一方、LLM の費用は実際にかかっているので記録を残す（予算ガードのため。007 の決定事項 2）。CLAUDE.md の記述も「送信なし・記事の状態を残さない」に直す。
2. **失敗したときも `llm_calls` を残す**：ロールバックの前に読み出して入れ直す。SQLite は書き込みを 1 つの接続しか持てないため、別の接続で先にコミットする方法は使えない。
3. **記事が 0 件の日はメールを送らない**：SPEC §7 の `digests.status = empty` に合わせる。取得の失敗は、次に記事がある日のフッターと、ログで分かる。0 件の日にも「0 件でした」と送ってほしい場合は変える。
4. **ダイジェストの送信に失敗したら、記事は既読のまま `sent` にしない**：翌日に同じ記事は再配信されない（SPEC §7「取得時点で既読」）。送信の失敗は失敗通知とログで分かる。
5. **終了コードは 0 / 1 / 2**：cron のログで失敗と二重実行を区別できるようにする。

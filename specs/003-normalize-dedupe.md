# 003: URL 正規化と既読判定

- 状態: 実装済み
- 関連: SPEC.md §4 の 2（正規化）、§5（`recheck_changed`）、§7（重複排除の方針 1・2、既読判定）、001、002

## 目的
取得した記事の URL を正規化し、DB の既読記事と照合する。初めて見た記事は、この時点で `articles` に記録する（配信するかどうかに関係なく、取得した時点で既読にする）。
これにより、同じ記事を 2 日続けて配信せず、翌日に再採点もしない（SPEC §13）。

## 範囲
- 含む:
  - 取得結果を表す型 `FetchedItem`（004 のフェッチャーが作り、この機能に渡す）
  - URL の正規化
  - `content_hash` の計算
  - 既読判定と `articles` への記録（`recheck_changed` による再収集を含む）
- 含まない:
  - フィードの取得そのもの：004
  - 別ソースの同一話題（タイトル類似度）の重複排除：006（SPEC §7 の方針 3）
  - 時間窓・キーワードによる絞り込み：005
  - `--dry-run` のときにコミットするかどうか：013（この機能はコミットしない。後述）

## 入出力
### FetchedItem（004 → 003）
| 項目 | 型 | 説明 |
|---|---|---|
| `source_id` | 文字列 | `sources.yaml` の `id` |
| `url` | 文字列 | 記事の URL（正規化前） |
| `title` | 空でない文字列 | 原題 |
| `published_at` | タイムゾーン付き日時、またはなし | 公開日時。フィードに無ければなし |
| `content` | 文字列（既定は空） | フィードに含まれる本文や抜粋。`content_hash` の計算に使う |

### 既読判定
- 入力: DB 接続、`FetchedItem` のリスト、ソース設定（`id` → ソース）、現在日時
- 出力: 今回処理を続ける記事（新規、または再収集）のリスト。各記事は DB の `id`、正規化した URL、`FetchedItem` の内容を持つ

## 振る舞い

### URL の正規化
1. スキームとホスト名を小文字にする。パスとクエリの大文字・小文字は変えない。
2. スキームの既定ポート（http の 80、https の 443）を取り除く。
3. フラグメント（`#...`）を取り除く。
4. 追跡用のクエリパラメータを取り除く。既定は `utm_` で始まるもの、`fbclid`、`gclid`、`yclid`、`mc_cid`、`mc_eid`。一覧は引数で差し替えられるようにする。
5. 残ったクエリパラメータは名前の順に並べる（同じ名前のパラメータどうしの順は保つ）。クエリが空になったら `?` も付けない。
6. パスの末尾のスラッシュを取り除く。パスが空またはルートだけなら `/` にする。
7. スキームが http / https でない、またはホスト名が無い URL は正規化できないものとする。
8. スキームの違い（http と https）や `www.` の有無はそろえない（別の URL として扱う）。

### content_hash
- `title` と `content` をそれぞれ、連続する空白（改行を含む）を 1 つの空白にまとめて前後の空白を取り除き、改行でつないだ文字列の SHA-256（16 進の小文字）とする。

### 既読判定と記録
入力の順に 1 件ずつ処理する。
1. URL を正規化する。正規化できなければ、その記事をスキップして WARNING ログを出す。
2. `source_id` がソース設定に無ければ、その記事をスキップして ERROR ログを出す。
3. 同じ正規化 URL の記事が、今回の入力ですでに処理済みならスキップする（先に来た記事を残す）。
4. 正規化 URL が `articles` に無ければ、次の内容で登録し、出力に含める。
   - `url`（正規化済み）、`source_id`、`category`（ソースの `category`）、`title`、`published_at`、`fetched_at`（現在日時）、`content_hash`、`status = new`
5. `articles` にあり、ソースの `recheck_changed` が `false` なら、スキップする（DB は変更しない）。
6. `articles` にあり、`recheck_changed` が `true` で、`content_hash` が同じなら、スキップする。
7. `articles` にあり、`recheck_changed` が `true` で、`content_hash` が変わっていれば、再収集する。
   - `title`、`published_at`、`content_hash`、`fetched_at` を更新し、`status` を `new` に戻し、前回の採点・要約の結果（`local_score`、`llm_score`、`final_score`、`matched_topics`、`summary_json`、`score_model`、`summary_model`）を消す
   - 出力に含める
8. この処理は DB をコミットしない。コミットするかどうかは呼び出し側（013 の CLI）が決める。

- 日時は UTC の ISO 8601 文字列で保存する（002 と同じ）。

## エラー時の挙動
| 状況 | 動作 |
|---|---|
| URL を正規化できない | その記事だけスキップし、WARNING ログに source_id と URL を出す |
| ソース設定に無い `source_id` | その記事だけスキップし、ERROR ログを出す |
| DB の操作で例外が起きた | 例外をそのまま呼び出し側に渡す（呼び出し側がロールバックする） |

## 受け入れ基準
### URL の正規化
- **AC-003-1**: Given `utm_source` などの `utm_` で始まるパラメータと、それ以外のパラメータを含む URL / When 正規化する / Then `utm_` のパラメータだけが消え、残りは名前の順に並ぶ
- **AC-003-2**: Given `fbclid`、`gclid`、`yclid`、`mc_cid`、`mc_eid` を含む URL / When 既定の一覧で正規化する / Then それらが消える。一覧を引数で差し替えると、差し替えた一覧に従う
- **AC-003-3**: Given フラグメント付きの URL / When 正規化する / Then フラグメントが消える
- **AC-003-4**: Given スキームとホスト名に大文字を含み、既定ポートを明示した URL / When 正規化する / Then スキームとホスト名は小文字になり、既定ポートは消え、パスとクエリの大文字・小文字は変わらない。既定でないポートは残る
- **AC-003-5**: Given パスの末尾にスラッシュがある URL、パスが空の URL / When 正規化する / Then 末尾のスラッシュは消え、パスが空ならルート `/` になる
- **AC-003-6**: Given 追跡パラメータしか無い URL / When 正規化する / Then `?` が残らない
- **AC-003-7**: Given http / https 以外のスキーム、またはホスト名の無い URL / When 正規化する / Then 正規化できないと判定される
- **AC-003-8**: Given 任意の正規化済み URL / When もう一度正規化する / Then 結果は変わらない

### content_hash
- **AC-003-9**: Given 空白や改行の入り方だけが違う `title` と `content` / When `content_hash` を計算する / Then 同じ値になる。`title` か `content` の中身が違えば、違う値になる

### 既読判定と記録
- **AC-003-10**: Given DB に無い URL の記事 / When 既読判定する / Then 振る舞い 4 の内容で `articles` に登録され、出力に含まれる
- **AC-003-11**: Given 同じ記事を 2 回続けて入力する（2 日続けて取得したことに相当） / When 2 回目を既読判定する / Then 出力に含まれず、DB は変更されない
- **AC-003-12**: Given `recheck_changed: false` のソースで、登録済みの URL に別の `content` の記事が来た / When 既読判定する / Then 出力に含まれず、DB は変更されない
- **AC-003-13**: Given `recheck_changed: true` のソースで、登録済みの URL に同じ内容の記事が来た / When 既読判定する / Then 出力に含まれない
- **AC-003-14**: Given `recheck_changed: true` のソースで、採点・要約済みの登録済み URL に別の内容の記事が来た / When 既読判定する / Then 振る舞い 7 のとおり更新され（`status` は `new`、採点・要約の結果は消える）、出力に含まれる。記事の `id` は変わらない
- **AC-003-15**: Given 正規化すると同じになる URL の記事が、1 回の入力に 2 件ある / When 既読判定する / Then 先に来た 1 件だけが登録され、出力に含まれる
- **AC-003-16**: Given 正規化できない URL の記事、または設定に無い `source_id` の記事を含む入力 / When 既読判定する / Then その記事だけがスキップされてログに残り、ほかの記事は処理される
- **AC-003-17**: Given 新規の記事を含む入力 / When 既読判定したあと、呼び出し側がロールバックする / Then DB は既読判定の前の状態に戻る（既読判定の処理自体はコミットしない）

## 実装方針（参考）
- URL の処理は標準の `urllib.parse` で行う
- `FetchedItem` は pydantic モデルにする（004 で外部データを検証して作るため）
- モジュールは `src/aidigest/pipeline/normalize.py`（正規化と hash）と `src/aidigest/pipeline/dedupe.py`（既読判定と記録）に分ける

## 決定事項
1. **追跡パラメータの既定の一覧**：`utm_*`、`fbclid`、`gclid`、`yclid`、`mc_cid`、`mc_eid` とした。`ref` は意味のある値に使うサイトがあるので含めない。一覧はいまは引数で差し替えられるだけで、設定ファイルには出さない（必要になったら追加する）。
2. **http と https、`www.` の有無はそろえない**：そろえると別の記事を同じと誤判定するおそれがあるため。同じ記事が別の URL で来た場合は、006 のタイトル類似度で除く。
3. **再収集したときに採点・要約の結果を消す**：内容が変わったので、もう一度採点し直すため。`sent` だった記事も `new` に戻るので、内容が変わったリリースノートなどは再配信されうる（SPEC §5 の `recheck_changed` の意図どおり）。

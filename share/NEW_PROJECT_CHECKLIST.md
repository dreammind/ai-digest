# 新規開発チェックリスト（Claude Code と進める場合）

先に広く調べて「作らない選択肢」を潰し、仕様は薄く固め、動く最小形を早く作ってから、機能ごとに「仕様 → テスト → 実装」を回す。

使い方: 新しいプロジェクトの最初にコピーし、終わった項目にチェックを入れる。`CLAUDE.template.md` は Phase 5 でプロジェクトに置く。

---

## 規模別の省略の目安
間違えたときの代償と規模に合わせて、重さを調整する。

| 規模 | 目安 | やること |
|---|---|---|
| 小 | 使い捨て・数十行のスクリプト | Phase 1 の一文だけ決めて、あとは作る。仕様もテストも不要（秘密情報を扱うなら Phase 5 の秘密情報の項目だけはやる） |
| 中 | 個人利用・数日〜数週間 | Phase 1〜10 を薄くやる。`specs/` は重要な機能だけ |
| 大 | 他人が使う・長期運用・お金や個人情報が絡む | すべてやる。Phase 8・9 の実環境での確認を厚くする |

---

## Phase 1. 目的と制約を一文で固める【人が決める】
- [ ] 何のために作るかを一文で書いた
- [ ] 成功の条件を書いた（何ができれば成功か）
- [ ] 制約を書いた（予算、期限、動かす環境、使える技術、運用にかけられる手間）
- [ ] やらないこと（非目標）を書いた

## Phase 2. 既存の解を先に調べる
- [ ] OSS・SaaS・既存ツールで足りないかを調べた
- [ ] 足りない場合、どこが足りないかを書いた
- [ ] 参考にする設計と、使わない部分を分けて書いた
- [ ] ライセンスを確認した。不明確なものはコードをコピーせず、考え方だけを取り込む
- [ ] 使う依存の最終更新日を確認した（目安: 直近 12 か月以内。外れるものは、理由を書いて承認を得る）
- [ ] 使う API やフィードは、実際に 1 回取得して、形・件数・制限（認証、レート制限、取得できる期間）を確かめた。推測で URL や項目名を書かない
- [ ] 調べた日付を残した（情報は古くなる）

## Phase 3. 決定事項を記録する【人が決める】
仕様の値には、必ず次のどれかを付ける。

- **[決定]**: 人が決めた。変えるときは確認する
- **[暫定]**: AI が置いた初期値、または自分が仮に置いた値。Phase 8 の実測で確定する
- **[未決]**: まだ決めていない。決めるまで実装しない（または仮実装と明記する）

チェック:
- [ ] 数値・しきい値・件数・上限は、すべて決定/暫定/未決のどれかにした
- [ ] 暫定値の一覧を、人が一度は目を通した
- [ ] 未決事項が仕様の末尾に集まっている

## Phase 4. 仕様を薄く書く（SPEC.md）【人が承認する】
- [ ] 目的、非目標、MVP の範囲、全体の流れを書いた
- [ ] 受け入れ基準を書いた（Given / When / Then。ID を付ける）
- [ ] 外部とやり取りする箇所と、失敗したときの動作を書いた（エラー時の動作を表にするなら、各行にも受け入れ基準の ID を付ける）
- [ ] 費用・性能・件数などの上限があれば書いた
- [ ] 詳細は `specs/NNN-<name>.md` に回すことにして、SPEC.md を長くしすぎていない（連番は既存のものと連続させる）

## Phase 5. 開発基盤を先に整える（Phase 0）
機能より先に、品質のルールを機械的に守らせる仕組みを置く。

### 秘密情報（最初のコミットより前に行う）
- [ ] 秘密情報の置き場所を `.env` などに決め、`.env.example`（値は空）を用意した
- [ ] `.gitignore` に `.env`、`.env.*`（`!.env.example` で見本だけ除外）、エディタの一時ファイル（`*.sw[a-p]`、`*~` など）を入れた
- [ ] pre-commit に、API キーらしい文字列を含むコミットを止める検査を入れた（見つけたときはファイル名だけを表示し、値を表示しない）
- [ ] `.claude/settings.json` の `permissions.deny` で、Claude Code が `.env` を読む・編集する操作を禁止した
- [ ] `git add` はパスを明示する（`git add -A` / `git add .` を使わない）というルールを `CLAUDE.md` に入れた

### 品質の仕組み
- [ ] リポジトリを作り、依存管理を決めた
- [ ] 型チェック、lint、テストを入れ、空のテストが通る
- [ ] `CLAUDE.md` を置いた（`CLAUDE.template.md` から作る。短く保つ）
- [ ] 会話の言語と、コミットメッセージの言語・詳しさを決めた
- [ ] よく使うコマンド（テスト、型チェック、lint、ログ確認など）を、タスクランナー（just / make など）のレシピにまとめた
- [ ] 確認なしで進めてよい操作と、必ず確認する操作を決めた（副作用のない確認系は確認不要にして、往復を減らす。push は確認する側に入れる）
- [ ] コミット前のチェック（pre-commit など）を入れた
- [ ] Claude Code の hooks で、編集後の lint・型チェックと、終了時のテスト実行を自動化した（終了時のテストは、実装に未コミットの変更が無い TDD の Red の段階では差し戻さないようにする）
- [ ] `README.md` に「機能と仕様の状態」と「改善の候補」の表を作った（機能ごとにセッションを分けても、続きから始められるようにする）
- [ ] 記録の置き場所を作った: バグ修正記録（`doc/BugHistory.md`）、振り返り（`doc/Retrospective.md`）

### 運用を見すえた設計
- [ ] 外部に影響するアプリ（メール送信、外部への書き込み など）なら、送信や記録を残さずに全体を試せる `--dry-run` を設計に入れた
- [ ] LLM を使うなら、このプロジェクト専用の API キーを作り、提供元の画面で利用上限を設定した
- [ ] LLM の呼び出しは 1 つのラッパーを通し、トークン数と費用を記録して、日・月の上限で止めるようにした

## Phase 6. 動く最小形を端から端まで通す
- [ ] 入力 → 処理 → 出力を、最小の形で一周させた
- [ ] 外部とのやり取り（API、メール、DB）はモックかフェイクでよい。ただし、モックの形は Phase 2 で実際に取得した応答に合わせる
- [ ] この時点で、つなぎ目の問題（データの形、順序、エラーの扱い）を洗い出した
- [ ] 洗い出した問題で仕様が変わる場合は、仕様を先に直した

## Phase 7. 機能ごとに回す（SDD → TDD）
1 つの機能ごとに繰り返す。

1. [ ] 仕様（受け入れ基準）を書き、承認を得た
2. [ ] 失敗するテストを書き、期待した理由で失敗することを確認した（Red。ここではコミットしない）
3. [ ] テストを通す最小の実装を書いた（Green）
4. [ ] テストが通ったまま整理した（Refactor）
5. [ ] チェックが通り、テストと実装をまとめて 1 つの `feat:`（修正は `fix:`）でコミットした（Refactor は `refactor:` として別にしてよい）
6. [ ] 完了の定義に沿って、仕様・README の状態の表・ドキュメント・お知らせなど、更新すべきものを更新した
7. [ ] 仕様・テスト・実装が一致している

注意:
- テストが失敗したとき、テストを書き換えて通さない
- 仕様にない変更が必要になったら、実装を止めて仕様の修正案を出す

## Phase 8. 実データで確認し、暫定値を確定する【人が決める】
- [ ] 外部サービスを使う機能を、実際のサービスで 1 回動かした（費用や副作用がある場合は承認を得てから。`--dry-run` があれば使う）
- [ ] 出力を人が読んで確かめた（モックでは見つからない問題：LLM の出力のスキーマ違反、文字としての `\n`、空の要素、文字化け など）
- [ ] 外部から来たデータの検証に失敗したとき、どの項目が違反したかがログで分かる
- [ ] 費用・時間・件数などを実測した
- [ ] 暫定値を見直し、[決定] に変えた（または調整した）

## Phase 9. 本番に配置する【人が確認する】
各手順は、実行前に人が確認する。

- [ ] 履歴に秘密情報が無いことを確かめてから push した
- [ ] 配置先で、ロックどおりに環境を作り、テストを通した（例: `uv sync --frozen`、`npm ci`）
- [ ] 配置先の `.env` を安全に送り（例: `ssh host 'umask 077; cat > path/.env' < .env`）、権限を 600 にした
- [ ] 配置先で `--dry-run` を 1 回実行した
- [ ] 定期実行（cron など）は、既存の設定をバックアップしてから足した。既存の行に触れず、コマンドは絶対パスで書いた
- [ ] 初回の定期実行の結果（届いたか、ログにエラーが無いか、実行の記録があるか）を確かめた
- [ ] 失敗したときに気づける仕組み（ログ、失敗通知）がある
- [ ] **実行されなかった**ことに気づける仕組みがある（外部の死活監視。例: 実行の最後に healthchecks.io などへ通知する。サーバーや cron が止まると、失敗通知も送られないため）
- [ ] DB などのデータのバックアップ方法を決めた
- [ ] 環境設定のガイド（例: `doc/Setup.md`）を書いた
- [ ] 文書にホスト名・ユーザー名・個人のパスを書かず、仮の名前（`my-vps`、`<ユーザー名>` など）にした（あとから消すと、履歴の書き換えが必要になる）

## Phase 10. 運用しながら振り返る
- [ ] 未決事項を消化した
- [ ] `SPEC.md`・`CLAUDE.md`・`README.md` を実態に合わせて更新した
- [ ] 修正したバグを、症状・原因・修正内容で記録した（対象はロジックのバグとデータの不整合。typo や軽微な修正は不要）
- [ ] 運用で気づいた改善の候補を、README の「改善の候補」に足した
- [ ] セッションの終わりに振り返り、`doc/Retrospective.md` に記録した（うまくいったこと／問題と対策／決めたこと／反映した先）
- [ ] うまくいかなかった点をルールか仕組み（`CLAUDE.md`、hooks、pre-commit、テンプレート）に変え、反映した先を記録に書いた（同じ失敗を繰り返さない）

## 人が判断する場面（まとめ）
1. 目的と制約（Phase 1）
2. 暫定値の確認と未決事項の決定（Phase 3、Phase 8）
3. 仕様の承認（Phase 4、Phase 7 の各機能）
4. 外部に影響する操作の実行（Phase 8 の実サービスでの実行、Phase 9 の配置・定期実行の登録）
5. GitHub などへの push（強制 push を含む）
6. 秘密情報が漏れたときの対応（下の「秘密情報が漏れたとき」）

それ以外は AI に任せ、判断が要る点が出たら止まって聞いてもらう。

## Claude Code に頼むときのコツ
- 最初に「計画だけ出して。コードはまだ書かないで」と頼み、計画を確認してから進める
- 1 回の依頼は小さくする（1 機能、1 テスト単位など）
- 機能（`specs/` の 1 つ）ごとにセッションを分ける。始めるときは「CLAUDE.md と README.md を読んで。〇〇に取り組みたい。まず specs/NNN の草案を書いて」のように頼む
- 曖昧な点は、推測で進めずに質問させる
- 秘密情報（API キー、パスワード）はチャットに貼らない。「`.env` に設定した」とだけ伝える
- `CLAUDE.md` は短く保つ。長い手順や詳細な仕様は `specs/` に分ける
- 同じ指摘を 2 回したら、`CLAUDE.md` か hooks に入れる
- セッションの終わりに「振り返りをして、doc/Retrospective.md に記録して」と頼み、出てきた改善を `CLAUDE.md`・hooks・このチェックリストとテンプレートに戻す

## 秘密情報が漏れたとき
コミットした、ログやチャットに出した、などに気づいたら、次の順に行う。**失効が先**（履歴から消しても、すでに見られた・複製された可能性は消えない）。

1. 提供元の画面で、漏れたキーやパスワードを失効させる
2. 新しいものを作り、`.env` に入れる（チャットには貼らない）
3. 履歴から消す（コミットの作り直し、`git filter-branch` / `git filter-repo`、reflog の削除と `git gc`）
4. push 済みなら、承認を得てから強制 push（`--force-with-lease`）し、配置先も合わせる（例: `git fetch && git reset --hard origin/main`）
5. 原因を、ルールか仕組みに変える（`.gitignore`、pre-commit の検査、`permissions.deny` など）

## 決定ログの書き方（SPEC.md の末尾などに置く）
```
## 決定ログ
| 日付 | 項目 | 内容 | 状態 | 理由・メモ |
|---|---|---|---|---|
| 2026-10-07 | 配信頻度 | 毎朝 1 通 | 決定 | 即時通知は不要 |
| 2026-10-07 | 1 回に選ぶ件数 | 8 件 | 暫定 | 費用の実測で見直す |
| 2026-10-07 | 送信サービス | - | 未決 | Gmail SMTP か配信サービスか |
```

# バグ修正記録

修正したバグを、新しいものを上に追記する（CLAUDE.md の「バグ修正記録」）。

- 記録する: ロジックのバグ、データの不整合
- 記録しない: typo の修正、軽微なテストの修正、リファクタリング
- 同じ種類のバグが繰り返されたら、CLAUDE.md にルールとして足す

---

## 2026-10-16 要約に文字としての `\n` が表示される

- **症状**: メールの要約と AI活用 に、改行ではなく `\n` という 2 文字がそのまま表示された（ユーザーが受信したメールで発見）。
- **原因**: 要約のプロンプトで「段落を分ける」よう指示すると、モデルが tool use の入力（JSON の文字列）に本物の改行ではなく、バックスラッシュと `n` を書くことがある。応答をそのまま使っていた。
- **修正内容**: 要約のスキーマ（`Summary`）の `summary` と `apply_to_claude_code` に、検証の前に文字としての `\n` を本物の改行に置き換える処理（`_real_newlines`）を入れた。仕様は specs/010 に追加。
- **コミット**: `863c52f`（テストは `83c8e13`）
- **教訓**: LLM の出力は、モックのテストでは見つからない形で崩れる。実際のサービスで 1 回動かし、出力を人が読む（CLAUDE.md の「完了の定義」）。

## 2026-10-16 `key_takeaways` が多すぎて要約ごと捨てられる

- **症状**: 実データで動かしたとき、一部の記事が「要約なし」になった。ログには「スキーマ違反」としか出ず、どの項目が原因か分からなかった。
- **原因**:
  1. モデルが `key_takeaways` を 7 件返すことがあり、スキーマの上限（5 件）に違反して、要約全体が不正とされていた（再試行しても同じ結果になりやすい）。
  2. 検証エラーのログに、違反した項目と理由を出していなかった。
- **修正内容**:
  1. `key_takeaways` と `topics` は、上限を超えたら先頭の 5 件に切り詰めてから検証する（`_first_items`）。件数だけを理由に要約を捨てない。
  2. 検証エラーのとき、違反した項目と理由をログに出す（`describe_validation_error`。入力の値は出さない）。再ランクの応答にも同じ処理を使う。
  - 仕様は specs/010 / 011 に追加。
- **コミット**: `9d0b78b`（テストは `59867ec`）
- **教訓**: 外部から来たデータの検証に失敗したときは、どの項目が違反したかをログに出す（CLAUDE.md の「完了の定義」）。直せる違反（件数の超過など）は、捨てずに直してから使う。

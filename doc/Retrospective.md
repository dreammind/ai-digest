# 振り返りの記録

セッションの終わりに振り返り、新しい回を上に追記する（CLAUDE.md の「振り返り」）。
決めたことは、それぞれの置き場所に反映し、「反映した先」に書く。

- ルール → `CLAUDE.md`、hooks、pre-commit
- これからやること → `README.md` の「改善の候補」
- アプリのバグ → `doc/BugHistory.md`
- 他のプロジェクトでも使えること → `share/` のテンプレートとチェックリスト

## 2026-10-15〜17 Phase 0〜Phase 1（MVP）の実装と VPS への反映

1 つのセッションで、初期化から 001〜014 の仕様・テスト・実装、VPS への反映までを行った（116 コミット、テスト 408 件、カバレッジ 99%）。

### うまくいったこと
- 機能ごとに仕様（受け入れ基準つき）→ テスト → 実装の順を守り、仕様と実装のずれがほとんど出なかった。
- pyright（strict）・ruff・pytest を hooks と pre-commit で自動化し、エラーを溜めずに進められた。
- 実際のサービスで動かしてから決めたことが多く、推測で作らずに済んだ（Zenn・Qiita の取得方法、HN の検索条件、要約の改行）。
- `--dry-run` があったので、VPS への反映と確認を、メールを送らずに安全に進められた。
- LLM の費用を記録し、日・月の上限を置いたので、費用の心配をせずに試せた（1 日 約 1.3 円）。

### 問題と対策
| 問題 | 原因 | 対策 |
|---|---|---|
| API キーをコミットし、さらに `git show` で値を表示した | `git add -A` で、未追跡の無関係なファイル（中身はキー）を巻き込んだ | キーを失効させ、コミットを作り直して reflog と gc で消した。`git add` はパスを明示するルール、pre-commit のキー検査、メモリへの記録 |
| vim のスワップファイル（`.env.swp`）が見つかった | `.gitignore` にエディタの一時ファイルが無かった | `.gitignore` に vim のバックアップファイルなどを追加 |
| 文書に VPS のホスト名とユーザー名を書いていた | 文書に実際の名前を書くことを気にしていなかった | 仮の名前（`my-vps`、`<ユーザー名>`）に置き換え、履歴を書き換えて強制 push |
| 確認せずに GitHub に push した | 確認の対象に push が書かれていなかった | CLAUDE.md の確認の対象に push を追加 |
| 説明が英語になった（2 回） | 会話の言語が CLAUDE.md に書かれていなかった | CLAUDE.md に「会話は日本語」を追加 |
| Stop hook が、TDD の Red の段階でも差し戻した | テストが失敗していれば一律に差し戻していた | `src/` に未コミットの変更が無ければ差し戻さないようにした |
| Red の段階でもコミットしていて、コミットが細かすぎた | コミットを `test:` → `feat:` に分けるルールにしていた | テストが通った段階で、テストと実装をまとめて 1 つのコミットにするルールに変更 |
| 実データで、LLM の出力の崩れが見つかった（件数の超過、文字としての `\n`） | モックのテストでは、モデルの実際の出力の崩れを再現できない | 直せる違反は直してから使い、違反した項目をログに出す（[BugHistory.md](BugHistory.md)）。実際のサービスで 1 回確認することを完了の定義に追加 |
| macOS で、`cp -i` が入力待ちで止まった、BSD の `sed` で置換されなかった | GNU の前提でコマンドを書いた | ファイルの編集は Edit ツールか Python で行う（Claude のメモリに記録） |
| セッションが長くなりすぎた | 全機能を 1 つのセッションで進めた | 機能（`specs/` の 1 つ）ごとにセッションを分ける。状態は README・`specs/`・履歴に残す |

### 決めたこと
- `git add` はパスを明示する。中身の分からないファイルを表示しない。
- GitHub への push も、実行前に確認する。
- Claude Code に `.env` を読ませない（`permissions.deny`）。
- コミットは、テストが通った段階で、テストと実装をまとめて 1 つにする。
- 外部サービスを使う機能は、実際のサービスで 1 回動かして出力を確かめてから完了とする。
- 仕様の状態と改善の候補は README で管理する。バグは BugHistory.md、振り返りはこのファイルに記録する。
- セッションの終わりに振り返る。
